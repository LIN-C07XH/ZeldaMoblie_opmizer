# v1.4.3 相机接入依据

## 来源与核对方式

起点是本地 `nx-optimizer/src/PatchInfo/Tears Of The Kingdom/UltraCam/exefs/subsdk3` 的 CameraControl / CameraControlFix / CameraFunc 字符串和特征码。它们分别指向当前游戏的通用矩阵构建路径、该路径所在更新函数，以及 SEAD 的相机辅助计算。不能因为宿主函数叫 SpringArm 就推断已经进入原生碰撞流程。

函数名称参考公开的 [dt-12345/totk_syms](https://github.com/dt-12345/totk_syms)。该表面向 **1.2.1**，这里只用名称帮助辨认结构；所有实际地址都重新在本地 **1.4.3** 中定位，未直接套用旧偏移。

通过 ExecutePlayerCameraChase 的 getName 字符串交叉引用找到虚函数表，再从 0x120 槽追踪到实际追踪相机代码。PlayerCameraPreUpdate 同样由其 getName、虚函数表及组件调用链确认。

## 原实现的问题

`main+0x62883c` 在通用矩阵计算中。那里 `d1/d2/d0` 是 Eye 的 X/Y/Z，`d3/d4/d5` 是目标的 X/Y/Z；旧代码把它们错当成 `d0/d1/d2` 和 `d5/d3/d4`。并且在到达旧 hook 之前，一部分 Eye/目标数据已写回相机对象。宿主显示线程异步写入另一帧的绝对 Eye 会导致同帧数据不一致，也会覆盖原生相机的输出。

原来的 `cameraUpdateSpringArm(..., collisionDistance)` 只在单元测试调用，实际运行的 CAM1 hook 没有从游戏获取碰撞距离，因此测试通过不能证明运行时会避障。`zelda_game_seconds()` 是帧步进累计计时，标题界面也增长，不适合判断已读档。滚动事件则直接调用了缩放接口。

## 验证边界

已自动验证生成跳板的 ABI、状态门禁、输入消费以及可执行文件构建/加载；不以这些测试宣称实机碰撞已经在全部场景验收。普通 Chase、能力选择瞄准与究极手抓取以外的瞄准、攀爬、骑乘等分支尚未接入角度增量，保留原生行为。实际穿模、跟随手感、剧情镜头与模式切换由实机测试确认。

## 原生锁定目标观察

PreUpdate 回调同步读取组件 `+0x96c`，即组件 `+0x490` 原生相机状态中的 `+0x4dc`。`0x87669c` 每帧先清零此状态；`0x876738–0x876d78` 检查玩家 AttentionSender 的状态与受锁保护的有效 client，确认存在后才设置 bit 0。回调只复制这个标志，不缓存或跨线程解引用敌人地址。原生目标消失超过 0.1 秒即释放宿主维持的 ZL，无目标时中键仅发送按住输入。新增指令锚点校验覆盖状态基址、调用位置、清零及置位指令。

这依赖游戏有效目标状态，不是独立扫描敌人列表或读取生命值；目标死亡后实际何时清理 client，以及究极手和各菜单的右摇杆手感仍需实机验收。

## 究极手抓取后直接角度接入（CAM8）

`ExecutePlayerCameraUltraHand` 虚函数表为 `0x3793ec0`，其 `+0x120` 槽指向 `0x23d8e74`，再跳到 Target 公共更新 `0x23d7140`。在 `0x23d7b70` 接入：这时其两种控制分支都已汇合，原 `x29-0x58` 是 `{radius, latitude, longitude}`（角度为度），随后 `0x23d7c94` / `0x23d7de8` 使用 `0x18b12ec` 转成请求位置，最后经过原生目标组合和碰撞。

跳板先校验本帧 execution 的虚函数表只匹配 UltraHand；锁敌及其他 Target 子类不进入宿主回调。PlayerCamera 组件通过究极手原生 `0xc6f6e0` / `0x1951320` 使用的 execution → owner → component 链取得，每层判空，不保留旧组件指针。宿主同步读取 Target 参数类型与原生 LatMin/LatMax getter（`0x18a4c0c`、`0x18a9544`、`0x18a9598`），保留继承参数及原生限制。修改局部角度，并同步 execution `+0xa4/+0xa8/+0xbc` 的角度累积值，距离、注视点和碰撞不被覆盖。离开或进入模式时丢弃旧角度增量。

`native_ultrahand` 配置可实时退回右摇杆；按住 R 的物体旋转和装备方向键始终优先使用原生右摇杆。CAM8 五个回调槽与 UI 桥分开，旧 CAM7 及更早模块会被拒绝，覆盖后须重新生成模块。测试覆盖严格 vtable 过滤、全部寄存器与状态保存、原生俯仰范围、累积器同步、输入只消费一次、模式进入和退出、配置回退及无效参数回退；不以离线测试宣称实机聚焦/旋转手感已验收。

手游模式复用默认 SPECIAL_SWITCH 按钮：仅当本帧究极手相机仍有效时显示“旋转”，按住发送 R，按钮上的单指拖动转发为右摇杆；离开该模式、隐藏按钮或取消触摸时释放。没有新增触摸震动。

## 究极手运行时诊断

Mac／iOS 共用输入实现默认输出限频的 `[CAMERA_ROUTE]`，仅在收到鼠标／触屏事件后报告，最多每秒一条；`[CAMERA_BRIDGE]` 标记已加载带诊断的宿主版本。Mac 会自动进入本次 session 的 `runtime.log`，无需额外设置环境变量。

`callbacks` 依次是生命周期、Chase、UltraHand 累计调用数；`native/stick` 是直接角度和摇杆回退输入事件数；`drops` 是三条回调因门禁清除非空角度输入的次数。`ultra_apply` 是保持或修改究极手角度的次数，`chase_release` 表示普通 Chase 更新清除了已取得的究极手角度控制。`reject` 最近一次究极手门禁的位：1 非游戏状态，2 未取得原生角度范围，4 参数无效，8 模式／实例／目标／时间连续性中断，16 设置关闭，32 按住原生摇杆操作键，64 锁敌。`ultra_angles` 记录最近一次究极手回调写入前后角度。计数仅反映回调与输入路径，不能证明最终显示相机已采用这些角度。

## 抓取前的能力选择瞄准

用户复现日志 `20261024T070822.966983Z-18209` 中，连续选择瞄准期间生命周期次数增加，但 Chase 不再增加、UltraHand 次数为零，输入持续走右摇杆回退。抓取后 UltraHand 回调开始持续执行并保持角度。因此此阶段不能靠修改抓取后的回调修复。

`ExecutePlayerCameraSpecialPower` 名称交叉引用为 `0x23d43fc`，虚函数表 `0x3793868` 的 `+0x120` 指向独立更新 `0x23d2d40`。新增 `0x23d380c` 跳板，仅接受这一虚函数表：原 `x29-0x58` 是最终局部极坐标，下一条 `0x23d3810` 调用原生极坐标转换，`0x23d3824` 再按本帧目标组合请求 Eye。距离、目标组合、FOV 及后续碰撞仍走原生代码。普通 Aiming／望远镜等子类不会进入此回调。此类是能力选择共用分支，未把它扩大到所有瞄准相机。

`0x23d28fc` 每帧取得、排序并规范化原生俯仰上下限，保存到 execution `+0x1ac/+0x1b0`。宿主只同步读取这些已计算的限制，不新增客体参数 getter 调用。直接角度同时对齐 `+0x50/+0x160`（平滑／目标俯仰）和 `+0x54/+0x164`（平滑／目标水平角）；不会使用抓取后相机的 `+0xa4/+0xa8/+0xbc`，也不写陀螺仪状态。抓取前后各自保留角度控制，模式／实例切换丢弃旧输入，R、实体手柄和配置回退释放控制。手机“旋转”按钮仍只在抓住物体后显示。

诊断 `selection=(calls,applied,drops,reject)` 独立记录本分支；拒绝位 1 为状态／原生参数无效，2 为连续性中断，4 为设置关闭、原生摇杆操作键或锁敌。`selection_limits` 是最近一次原生范围。相机桥扩为 CAM8（56 字节），位于 `0x3ae4040..0x3ae4077`，不与 `0x3ae4080` 的 UI 桥重叠；需要重建三个客体模块和宿主应用。


## 原生宽屏输出与 HUD

原生 `0x3de5f8` 只取得尺寸上限。启动路径在 `0x8c63cc`（即将调用 `0x8c66ec`）接入，后续分辨率选择在 `0x3dcbe0` 接入。回调建立匹配屏幕的逻辑裁切，但保留固定显示纹理的尺寸上界；原生 SetResolution 不会扩展显示纹理。例如 1920×1080 的显示纹理使用 1912×880 逻辑视口，避免原先 2352×1080 请求越界。相机投影、游戏视口和 UI 布局同步使用逻辑比例，宿主始终等比呈现。

原生 `Projection::updateMatrix`（`0x6dfd64`）会把透视矩阵计算内联到 `0x6dfedc..0x6dffa4`，不会调用备用的 `0x27d5438` 方法。`getProjectionMatrix`（`0xc4710`）另有独立的 dirty 检查及内联透视计算（`0xc4754..0xc4804`），也不会调用 updateMatrix；原始镜像有 53 个直接调用点。因此仅拦截 updateMatrix，即使输出已是 1912×880，经 getter 取得的投影仍可能是 16:9，形成拉伸。

场景更新另在 `0x98918`（对象 x21）和视锥更新 `0x64a0ec`（对象 x20）各有一份独立内联计算，透视分支分别位于 `0x990f4` 和 `0x64aeac`；这两处通过重定位 GOT `0x396fc00` 读取计算方法地址，不能只搜索 ADRP+ADD 常量引用。仅覆盖两个公共入口时，同一相机可能在后续内联路径写回旧比例，造成静止时也在两种比例间闪烁。

CAM8 在四条路径的 dirty 检查前取得本次调用的活投影对象，以虚表 `+0x58` 的透视计算方法 `0x27d5438` 识别投影布局（也接受同一计算方法的派生类），并且只调整原版 16:9 或当前目标比例；正方形离屏相机和 OrthoProjection 保持原值。四条路径复用 `+0x30` 回调槽，不改变共享 ABI；必须重新生成模块并重建应用。回调修改 `+0xb0` 与 dirty bit；比例字段已匹配但缓存矩阵的横纵比例不一致时，也使缓存失效。之后由各自的原生内联路径计算矩阵，纵向 FOV 和近远平面保持原值。不缓存对象，不读取角色或相机 blackboard，也不读取图节点的连接端口。

宽屏最终显示只修正 8 像素对齐产生的小于 1% 比例差，保留整个图像；若实际输出仍为 16:9，会明确退回 Fit，不能以拉伸或裁切伪装成功。UIKit 的键位提示叠层同样使用实际输出尺寸。原生 HUD（特别是对话框和字幕）的最终位置、触控安全区与视频仍需用户试玩；离线矩阵和尺寸测试不能代替此验收。

### 输入与投影回调分离

Chase／生命周期保持三参数输入 ABI。角色组件 `+0x8b8`、PlayerCamera 输入 blackboard `+0x428` 与图连接端口均不是渲染投影对象，不能从这些字段推导对象地址。测试覆盖两次真机崩溃数据、独立的原生矩阵回调、全部寄存器保存，以及用户本地游戏四条路径的原始指令（已缓存与待更新两种状态）。回归测试保留“只拦截 updateMatrix”的旧行为作为对照；补齐 getter、场景与视锥路径后，1912×880 输出的横纵像素比例为 1，纵向 FOV 不变，原水平边界外的测试点进入视野。实机启动、摇杆及进入存档后的画面比例须另外验证。

`[DISPLAY_PROJECTION]` 每秒记录回调、参数修正、宽屏字段与旧矩阵缓存不一致的次数及采样比例；`[DISPLAY_PRESENT]` 每秒记录实际源尺寸、尺寸变化次数和最终视口，用于区分投影闪烁与呈现尺寸交替。这些计数不替代实机画面验收。

## UI 与标题画布比例

实机在标题界面采样确认：普通 UI 的 DrawInfo 虚表为 `0x391ae68`，`+0x10` 保存投影矩阵，m00=`1/960`、m11=`1/540`，即独立的 1920×1080 正交画布；它不是前述 SEAD 场景相机。将画布输出到 1912×880 而只调整场景相机，会使 UI 横向拉伸。

在 `Layout::Draw` 的 `0x10c7190` 接入 ZUI143 ABI 4 的 kind 4 回调，直接使用本次 x1 DrawInfo。入口已通过原生根节点判空；回调在原生 `0x10cc850` SetLayout 清理绘制状态之前执行，随后照常调用根节点的 Draw。只匹配已采样的 UI 虚表、居中的 1920×1080 正交矩阵和有限参数；其他画布、裁切投影、透视和场景正交相机保持原值。

UI 保留原版设计画布并等比居中：宽屏只缩小投影的横向系数，窄屏只缩小纵向系数；纵深、平移、节点变换及动画保持原生数据。不把现有 UI 节点重排到屏幕边缘。标题与菜单不依赖 PlayerCamera 生命周期。相同矩阵重复进入多个 Layout 不会累计缩小；每次原生重新提交设计矩阵时重新适配。键位提示叠层使用对应的等比设计画布定位。

C 测试覆盖手机／平板像素比例、标题状态、幂等性与拒绝非目标矩阵；原始指令测试覆盖 Layout → SetLayout → 根节点 Draw → 清理路径，验证最终绘制接收到修正的矩阵。真机 `UI_PROJECTION` 日志标记首次实际采用的 UI 修正，具体菜单及 HUD 仍须逐项试玩确认。
